# Как выбирать проверки

Решение владельца, 30.09.2026: проверки соответствуют масштабу изменения. Не запускать полный браузерный прогон для каждой небольшой правки и не повторять уже прошедшие проверки без конкретной причины.

| Изменение | Достаточная локальная проверка |
| --- | --- |
| Документация, контекст, правила | `git diff --check`; документационный коммит `[skip ci]`, без сборки и изменения `dist/` |
| Текст или данные отдельных страниц | `npm run verify`, сверка изменённых значений и ссылок; адресная проверка переноса/отображения изменённого блока |
| Изображение или оформление отдельного блока | Сборка, адресная проверка загрузки, размеров и отображения на desktop/mobile и затронутых брейкпоинтах |
| Один общий элемент, например H1 | Проверка этого элемента на затронутых семействах и нужных ширинах, без повторного тестирования остальных блоков |
| Навигация, общая интерактивность, шаблоны, рендеринг, глобальные шрифты/сетка | Полный браузерный прогон, если область возможных регрессий нельзя сузить |
| Изменения с влиянием на загрузку или первый экран | Lighthouse затронутых маршрутов; полный Lighthouse при системном влиянии |

Перед запуском назвать затронутые страницы, элемент/поведение и причину выбранных проверок. Проверка одного H1 не включает повторное раскрытие всех FAQ, просмотр всех галерей или проверку неизменённых прайсов на каждой странице. Штатные 11 ширин использовать, когда изменены общие переносы или адаптив; для небольшой редакции текста обычно достаточно desktop/mobile и конкретной проблемной ширины.

Для адресного прогона использовать `BROWSER_ROUTES`, например `/remont/kamaz/,/arenda/avtokrany/`; для Lighthouse — `LIGHTHOUSE_ROUTES`. Оба фильтра принимают главную `/` и эталонный hub `/remont-gruzovyh-avtomobiley/`. В адресном браузерном режиме выполняются контракты выбранных маршрутов и 404; pointer-навигация проверяется на выбранных страницах при 1440 px. Неизменённые главная, эталон и полный матричный сценарий общего меню не запускаются. Lighthouse требует production-like сборку; после неё вернуть `dist/` в preview перед публикацией сайта.

Critical CSS пересобирать при изменении оформления или состава первого экрана. Для обычной редактуры текста ниже первого экрана это не нужно. Не добавлять новые тесты, зеркалящие простую обратимую замену текста; обновлять существующий контракт, если меняется защищённое значение.

## Адресный CI — решение владельца 01.10.2026

`.github/workflows/deploy-pages.yml` всегда выполняет быструю сборку и проверку целостности. `tools/select-ci-scope.js` выбирает область дорогих browser/Lighthouse-проверок; их пороги остаются прежними.

| Изменение | Автоматическая область |
| --- | --- |
| JSON одной страницы | Только её маршрут |
| Отдельные contact/company/certificates/policy CSS, critical CSS или HTML-шаблон | Маршруты соответствующего оформления |
| CSS, partial или HTML только главной | Главная |
| Фото или PDF | Страницы, ссылающиеся на файл напрямую или через CSS; если связь не найдена — полный прогон |
| Общие стили, меню, JS, генератор, manifest, зависимости, неизвестный файл | Все маршруты |
| Только документация или инфраструктура выбора проверок | Без browser/Lighthouse и без повторной публикации; проверки самого селектора и сборка сохраняются |

База сравнения — последний успешный deployment среды `github-pages`, не предыдущий push. Если выпуск не прошёл, следующий включает и его незавершённые изменения. При недоступной истории, API или непонятной области применяется безопасный полный прогон. Генерируемый `dist/` не расширяет область при наличии исходников; правка только `dist/` запускает полный прогон. В `tools/build.js` допускается исключить только доказанную замену строки assetVersion, но не изменения генератора рядом с ней.

Ручной Actions → Deploy GitHub Pages → Run workflow сохраняет включённый по умолчанию `full_checks`. Отчёт шага «Select affected routes» показывает базовый SHA, режим, маршруты и причину полного запуска. Локальные проверки выбора: `node tools/test-ci-scope.js`; диагностика конкретного выпуска: `node tools/select-ci-scope.js --base <deployed-sha> --head <commit-sha>`.

Документационные коммиты `[skip ci]` по-прежнему не запускают workflow. Изменения CI проверять собственными тестами и адресным интеграционным запуском, не добавляя полный Lighthouse для неизменённого UI.

Прошедший этап повторяется только после новых изменений в проверяемой области, выявленной ошибки или конкретного нерешённого риска. Ожидание deployment и проверка публичного результата нужны для изменений сайта; для документации достаточно успешного push.
