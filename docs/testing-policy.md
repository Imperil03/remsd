# Как выбирать проверки

Решение владельца, 30.09.2026: проверки соответствуют масштабу изменения. Не запускать полный браузерный прогон для каждой небольшой правки и не повторять уже прошедшие проверки без конкретной причины.

| Изменение | Достаточная локальная проверка |
| --- | --- |
| Документация, контекст, правила | `git diff --check`; документационный коммит `[skip ci]`, без сборки и изменения `dist/` |
| Текст или данные отдельных страниц | `npm run verify`, сверка изменённых значений и ссылок; адресная проверка переноса/отображения изменённого блока |
| Изображение или оформление отдельного блока | Сборка, адресная проверка загрузки, размеров и отображения на desktop/mobile и затронутых брейкпоинтах |
| Один общий элемент, например H1 | Проверка этого элемента на затронутых семействах и нужных ширинах, без повторного тестирования остальных блоков |
| Навигация, общая интерактивность, шаблоны, рендеринг, глобальные шрифты/сетка | Полный браузерный прогон, если область возможных регрессий нельзя сузить |
| Изменения с влиянием на загрузку или первый экран | Lighthouse затронутых маршрутов; полный Lighthouse при системном влиянии |

Перед запуском назвать затронутые страницы, элемент/поведение и причину выбранных проверок. Проверка одного H1 не включает повторное раскрытие всех FAQ, просмотр всех галерей или проверку неизменённых прайсов на каждой странице. Штатные 11 ширин использовать, когда изменены общие переносы или адаптив; для небольшой редакции текста обычно достаточно desktop/mobile и конкретной проблемной ширины.

Для адресного прогона дополнительных внутренних страниц использовать `BROWSER_ROUTES`, например `/remont/kamaz/,/arenda/avtokrany/`; для Lighthouse — `LIGHTHOUSE_ROUTES`. Фильтр браузерного инструмента пока не принимает главную и эталонный hub: для их небольших изменений делать целевую проверку блока в браузере, а не возвращаться к полному прогону только из-за ограничения фильтра. Lighthouse требует production-like сборку; после неё вернуть `dist/` в preview перед публикацией сайта.

Critical CSS пересобирать при изменении оформления или состава первого экрана. Для обычной редактуры текста ниже первого экрана это не нужно. Не добавлять новые тесты, зеркалящие простую обратимую замену текста; обновлять существующий контракт, если меняется защищённое значение.

Текущий `.github/workflows/deploy-pages.yml` автоматически выполняет полный браузерный прогон и Lighthouse всех содержательных страниц при публикации сайта. Это отдельная обязательная проверка CI, которую не нужно дублировать локально без причины. Этот выпуск правил не изменяет workflow. Документационные коммиты `[skip ci]` не запускают новую публикацию сайта.

Прошедший этап повторяется только после новых изменений в проверяемой области, выявленной ошибки или конкретного нерешённого риска. Ожидание deployment и проверка публичного результата нужны для изменений сайта; для документации достаточно успешного push.
