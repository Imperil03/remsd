## Запуск на другом компьютере

Нужны Git и Node.js 22, который используется и в CI. Клонировать репозиторий в любой каталог:

```bash
git clone https://github.com/Imperil03/remsd.git
cd remsd
git switch main
npm ci
npx playwright install chromium
npm run verify
```

На Linux системные зависимости браузера устанавливаются командой `npx playwright install --with-deps chromium`, как в CI.

В существующей копии сначала проверить `git status`, затем получить изменения через `git pull --ff-only`. Если есть локальные правки или расходящаяся история, сохранить и совместить их; не заменять рабочую копию вслепую. Для параллельной задачи подходит отдельный worktree от актуальной `origin/main`.

Открыть корень клонированного репозитория в новом Codex и начать с `AGENTS.md` и этого файла. Переносить старые локальные пути, `node_modules`, `test-results` или историю чата не требуется. Зависимости устанавливаются из lock-файла, скриншоты и отчёты создаются проверками. Доступ для push в GitHub настраивается на новом компьютере отдельно; секреты в репозитории не хранятся.

Команды браузерной проверки, production-like Lighthouse и возврата `dist/` в preview находятся в `README.md`. Для проверки компании в PowerShell:

```powershell
$env:BROWSER_ROUTES = "o-kompanii"
npm run test:browser
Remove-Item Env:BROWSER_ROUTES
```

В Bash эквивалент: `BROWSER_ROUTES=o-kompanii npm run test:browser`. Если меняются общие документы, добавить маршрут `sertifikaty`. После изменения hero, показателей или шрифтов выполнить `npm run build`, `npm run generate:critical`, `npm run verify`. В коммит входят исходники и обновлённый preview `dist/` без sitemap.

- `site-chrome.css` — общая навигация, кнопка, callbar, шапка, футер и служебная 404;
- `styles-v3.css` — только главная;
- `internal-pages.css` — страницы ремонта и марок;
- `company-page.css` — страница компании.

Публичные бандлы: `base.css`, `home.css`, `internal.css`, `company.css`, `contact.css`, `certificates.css`. Контракт проверяет `tools/check-design-system.js`. Главная, страницы ремонта, компания, контакты и сертификаты имеют собственный critical CSS; эквивалентные объявления шрифтов не повторяются в отложенном бандле. `document-ui.css` входит в бандлы компании и сертификатов.

`src/data/internal-pages/index.json` — manifest схемы v3 с `referenceByFamily`; каждая страница хранится отдельным JSON. Семейства — `hub`, `service`, `brand`, `company`, `contact`, `documents`. 16 страниц ремонта используют `template: "repair-v1"`, а 23 страницы марок — `brand-v1`; базовый порядок обоих шаблонов содержит 11 смысловых секций, а явный `omitSections: ["symptoms"]` сокращает страницу до 10. Общие hero-факты, показатели, марки, этапы и контакт FAQ задаются только в `page-templates.json`. Компания не использует ремонтный шаблон и `metadata.serviceType`: её шесть внутренних секций вместе с hero и контактами образуют восемь блоков. Документы имеют только компактный hero и каталог, разметку `CollectionPage` и существующую сущность `proof-certificates`. Сущности и обе стороны отношений валидируются до сборки.

## Как добавлять следующую страницу

1. Определить интент и семейство страницы.
2. Подтвердить факты и текст по `.agent/SEO_STRUCTURE.md`.
3. Для аналогичной ремонтной страницы взять исходник с `template: "repair-v1"`, не копировать общие данные. Добавить отдельный `PageDefinition` в `src/data/internal-pages/` и включить его в manifest.
4. Переиспользовать существующие секции; новый тип секции вводить только для повторяемой задачи.
5. Сделать ссылку интерактивной только после появления маршрута в сборке. Количества работ и FAQ брать из утверждённого материала, не доводить искусственно до эталона. Для отдельной волны добавить приватный контентный fixture; общий PageDefinition не менять.
6. Выполнить `npm run build`, `npm run generate:critical`, `npm run verify`, `npm run test:browser`, `npm run test:lighthouse`, `git diff --check`.

Не создавать тонкие страницы формата «услуга × марка» без отдельного решения и достаточной фактуры.
