# AGENTS.md

## Проект

РемСД — статический сайт сервисного центра по ремонту грузовых автомобилей и спецтехники в Сургуте.

Репозиторий: https://github.com/Imperil03/remsd, основная ветка — `main`. Инструкция для нового компьютера и итог последнего выпуска — `docs/project-handoff.md`. Контекст хранится в репозитории; локальная история чата для продолжения не требуется.

Рабочий продакшен-превью:
- GitHub Pages: https://imperil03.github.io/remsd/

Внешний домен компании:
- https://remsd.ru/

## Главный SEO-фокус

1. Главная страница: ремонт грузовых автомобилей в Сургуте.
2. Главная страница: ремонт спецтехники в Сургуте.
3. Официальный сервис и ремонт КАМАЗ, МАЗ, УРАЛ в Сургуте — отдельный брендовый коммерческий слой и proof-сигнал на главной.
4. Ремонт агрегатов грузовых автомобилей и спецтехники: двигатель, ГБЦ, КПП, ходовая, тормоза, гидравлика, электрика, топливная система, охлаждение, SCR/AdBlue, ТО.
5. Аренда спецтехники — отдельное направление, не смешивать с ремонтом.

## Как работать

- Сначала читать `.agent/SEO_STRUCTURE.md`, `docs/project-handoff.md` и `docs/project-history.md`.
- Перед визуальными изменениями читать `docs/design-guideline.md`, затем `docs/design-system.md` и `DESIGN.md`.
- Перед продолжением получить актуальную `main` и проверить `git status`; не переносить старую рабочую копию поверх новых коммитов. При параллельной работе использовать отдельный worktree и сохранять чужие изменения.
- Не добавлять отдельные страницы вида `/remont-gbc-kamaz/`, `/remont-kpp-maz/`, `/remont-elektriki-ural/` без отдельного решения.
- Новые страницы сначала отнести к семейству `hub`, `service`, `brand`, `company`, `contact` или `documents`, затем добавить сущности, отношения, отдельный `PageDefinition` в `src/data/internal-pages/` и его имя в manifest `index.json`. Контракты компании, контактов и документов — `docs/company-page.md`, `docs/contact-page.md` и `docs/documents.md`.
- Выбирать проверки по масштабу изменения по правилам ниже и `docs/testing-policy.md`.

## Проверки по масштабу изменения

Решение владельца от 30.09.2026: для небольших изменений достаточно сборки, проверки данных и адресной проверки затронутых страниц. Полный прогон после каждой правки избыточен.

- Только документация, контекст или правила: `git diff --check`; без сборки, браузерного прогона, Lighthouse и пересборки `dist/`. Документационные коммиты отправлять с `[skip ci]`.
- Небольшие правки текста, данных, изображения или отдельного блока: `npm run verify`, проверка изменённых значений/ссылок и адресная проверка затронутых страниц или блока. Desktop и mobile обязательны при изменении отображения; дополнительные ширины — только для затронутых переносов и брейкпоинтов. Не проверять заново неизменённые FAQ, галереи, цены и другие сценарии.
- Изменение одного общего элемента, например H1: проверить этот элемент на затронутых семействах и нужных ширинах. Общий CSS сам по себе не требует полного прогона всех остальных блоков.
- Полный `npm run test:browser` нужен для изменений общей навигации, интерактивности, шаблонов, рендеринга или глобальной системы оформления, когда возможные регрессии нельзя надёжно ограничить конкретным элементом или набором страниц.
- Lighthouse запускать при изменениях загрузки, первого экрана, шрифтов, изображений, CSS или JavaScript, способных повлиять на производительность; выбирать затронутые маршруты. Полный Lighthouse — только при системных изменениях с широким влиянием.
- Прошедшие проверки не повторять без новых изменений в проверяемой области, ошибки или конкретного нерешённого риска. Не писать новые тесты только для подтверждения простой обратимой замены текста.
- GitHub Actions выбирает затронутые маршруты относительно последнего успешного Pages deployment: отдельная страница или изолированный CSS проверяются адресно. Общие стили, меню, генератор, manifest, зависимости и неизвестные изменения включают полный прогон. Смена только cache-buster не расширяет область проверки. CI/context-only изменения не публикуют сайт повторно. Подробности и ручной полный запуск — `docs/testing-policy.md`. Не дублировать прошедшие проверки локально ради самого факта публикации.

## Деплой

По указанию владельца от 30.09.2026 проверенные правки сразу коммитить и отправлять в `main` на GitHub: владелец проверяет результат на GitHub Pages. После push дождаться deployment и проверить публичный URL.

`dist/` отслеживается в git и используется GitHub Pages workflow. После сборки нужно коммитить и исходники, и обновленный `dist/`.

Если меняется оформление, шрифты или состав первого экрана, пересобрать critical CSS: `npm run build`, `npm run generate:critical`, `npm run verify`. Перед коммитом вернуть `dist/` в preview без sitemap. Публикация подтверждается успешным GitHub Actions deployment и проверкой страницы по публичному URL; успешный push сам по себе не означает публикацию.

Для правок только документации/правил не пересобирать сайт и не ждать нового deployment: коммит `[skip ci]` обновляет контекст репозитория. Critical CSS пересобирать, когда изменение затрагивает оформление или состав первого экрана; обычная редактура текста вне первого экрана этого не требует.

## Project Skills

- Vendored skills больше не хранятся в `.agent/skills/`. Не восстанавливать их без отдельного запроса.
- Перед работой с дизайном или текстами читать `docs/skills.md`, `.agent/SEO_STRUCTURE.md` и `docs/design-guideline.md`.
- Для публичного русского текста использовать цепочку: `SEO_STRUCTURE` -> существующий контент и явно указанные источники фактов -> спокойная B2B-редактура -> reviewer для SEO/коммерческих текстов.
- Внешние skills текущей Codex-сессии носят рекомендательный характер. Они не должны перебивать B2B-стиль РемСД, SEO-структуру, фактический тон и запрет на фейковые цены, сроки, гарантии, рейтинги, отзывы и манипулятивную срочность.
